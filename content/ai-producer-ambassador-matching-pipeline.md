## The problem: matching Gen Z students with AI ambassadors

I was a software engineer intern at AI Producer, based in Bellevue, Washington, from June to September 2025, working alongside one other intern and several engineers. The initiative I worked on was about helping Gen Z students, ages 18 to 21, feel safe and comfortable engaging with AI. The approach was an ambassador program: students would receive personalized mentorship on machine learning concepts and tools from ambassadors, people with real AI expertise or familiarity with AI tools. Once we settled on that approach, the engineering problem was determining which ambassadors were actually the best fit for each student. It wasn't as simple as matching identical profiles: students and ambassadors gave different kinds of information, a lot of the student side came through free-form text, some matching criteria were hard constraints, and others, like interests, goals, and areas of expertise, were semantic and much harder to compare deterministically. The challenge became designing a system that could take these asymmetric profiles, normalize them into something comparable, retrieve strong candidates efficiently, and return a small number of matches we could actually explain and validate.

## Why the system decides matches instead of just recommending options

One of the first design questions was whether the system should recommend a set of possible ambassadors and let the student choose, or actually determine the strongest matches itself. I looked at platforms like Preply and italki, where users see a set of tutors and pick themselves. Our case was different: we wanted the system to narrow the candidate pool and identify the ambassadors most appropriate for a given student. I brought the problem to senior engineers, our AI director, and our VP, and we concluded that a language model shouldn't control the entire matching process. Some parts of the problem were far more reliable as deterministic rules, and other parts, mainly the semantic reasoning about fit, were genuinely where a model added value. That distinction, deterministic where correctness is provable and a model only where semantic judgment is needed, became the design principle behind the whole pipeline.

## What the prototype was built with

The matching system was a prototype, written in plain Python with Pydantic for validating data at every stage and NumPy for the vector math, and run locally in-process through a command-line interface. I considered LangGraph and an agent SDK and decided against both: the control flow is an ordinary driver, not an agent. Every model call used OpenAI's gpt-4o-mini (the 2024-07-18 snapshot) at temperature 0 with structured outputs, so each response came back in a fixed schema instead of free text. Embeddings were held in memory as a NumPy matrix and searched exactly, with no vector database, which is reasonable at a few dozen profiles. The keyword search was a BM25 implementation I wrote to run in memory. This is the stack as recorded in my design document.

## The six-stage pipeline

The pipeline takes one student profile and returns five ambassador matches with defensible reasons for each. It runs as six stages coordinated by a driver, deterministic control flow rather than an agent, that routes based on a typed result each stage returns (ok, retryable, repairable, degraded, or fatal). Stage one validates the incoming profile against a schema. Stage two normalizes it: because student and ambassador profiles had asymmetric schemas and students could submit free-form answers, this stage converts that text into a consistent, structured representation. Stage three retrieves candidates deterministically. Stage four reasons over the narrowed candidate set and picks the final five. Stages five and six validate the output's schema and verify its claims before it's returned.

A language model is used in exactly three places. The normalizer uses one, because turning messy prose into structured attributes is a language problem, but it runs when a profile is written and its result is cached, so it isn't repeated on every match request. The matcher in stage four is the one model call every request is guaranteed to make. A critic model checks the matcher's output, but only on sampled outputs that have been flagged, not on every request. Once profiles are normalized, a typical match request costs a single model call.

## How retrieval narrows the candidate pool before any model call

Rather than sending the entire ambassador population to a language model, I built retrieval to narrow the field deterministically first. It ranks ambassadors four separate ways. Two are dense embedding searches: one compares the career path a student is aiming for with the paths ambassadors have actually taken, and the other compares the kind of help the student is asking for with what ambassadors offer. The third is keyword matching with BM25, which catches exact terms that embeddings can miss. The fourth is an entity-anchor score that weights shared attributes by rarity, so two people who both come from an unusual background score higher than two people who both merely mention something everyone lists.

The four rankings are merged with weighted reciprocal rank fusion. Each list contributes according to the position an ambassador holds in it, not the raw score, because cosine similarity, BM25, and the anchor score sit on scales that can't be meaningfully added together. Each channel has a weight inside the fusion: 1.0 for the career-path search, 0.6 for the help-offered search, 0.7 for keyword matching, and 1.2 for entity anchors, with the standard fusion constant of 60. The merged list is then diversified with maximal marginal relevance, so the candidates handed to the model aren't twenty near-identical profiles. That brings the field down to roughly twenty candidates before the matcher reasons over them and selects the final five.

## Debugging retrieval that looked plausible but wasn't right

The hardest problem I hit was in retrieval, and it didn't look like a bug. My first approach was the standard one: embed the student's profile, embed each ambassador's profile, and retrieve nearest neighbors by cosine similarity. The results weren't obviously broken. They were plausible people, just consistently not the ones I'd have expected to be strongest, and with no exception or bad output to trace, that was harder to work on than an error would have been.

My first instinct was that it was a tuning problem, so I padded sparse profiles with more context and adjusted how much each search signal counted. Neither helped. That's when I changed how I was debugging: I broke the pipeline into separate questions. Were we representing what the student actually needed? Was the similarity search finding what that representation pointed to? Were we ranking the results appropriately afterward? I focused on the boundary between representation and retrieval, because we were assuming that embedding a student's profile would place it near the ambassadors best suited to help them, and describing someone's interests isn't the same as describing the person who could help them.

To test that assumption, I simplified the search: I took one student vector and looked at its nearest neighbors without restricting the results to ambassadors. Almost all of them were other students. The embedding was capturing similarity between people expressing similar needs, not compatibility between a student's needs and an ambassador's experience. So I changed the query to describe the ambassador we wanted to find, built from the student's normalized goals, while keeping the encoder and index the same. A student who wrote "sophomore CS major, did some ML class projects, wants to get into AI, needs interview help" became two queries: one describing a career path (AI engineer, applied ML, retrieval-augmented generation, AI lab) and one describing the help needed (interview prep, portfolio review). That split is where the two separate dense searches come from.

I judged the change by recall at 20 against hand-labeled examples, because retrieval is a hard ceiling on everything after it: if the right ambassador never makes the shortlist, the matcher can't recover them. I don't have those numbers on record anymore, so I can't quote how much it improved. The lesson I took from it is that not every bug is broken code. The implementation did exactly what I designed it to do; the mistake was an assumption about what the two embeddings represented. Now, when a system produces reasonable-looking but consistently wrong output, I inspect the intermediate representation before I start tuning the logic around it.

## The data model: keeping current, target, and transitions separate

Normalization produced a data model that kept several things deliberately separate. For students, I split what they currently are (current), what they want to become (target), and what kind of help they're asking for right now (seeks), because a student wanting to become a product manager and a student wanting a single portfolio review are different requests that shouldn't be scored the same way. For ambassadors, I stored their full ordered career history, not just their current role, and derived transitions (for example, engineer to product manager) directly from that sequence. That let the system match a student who wants to move from engineering into product with an ambassador who actually made that specific move, not just any current product manager. Since most 18 to 21 year old students don't have a current role yet, I also supported a wildcard-origin match, anyone who ended up at the student's target regardless of their starting point, so the system still had something to anchor on for students earliest in their path.

## Resolving ambiguous language into a fixed taxonomy

Matching on free text directly means counting typing conventions instead of shared experience, so I built a fixed taxonomy: a table of ids like role:product_manager, with a set of surface names that all resolve to it. This resolution is part of the normalizer, and it works in two tiers. An exact alias lookup handles the common case instantly and at no cost. For genuinely ambiguous terms, like an acronym that means different things depending on context, a model looks at the surrounding sentence and picks from the nearest candidate ids, or returns none rather than guessing; anything it can't place goes to a review queue instead of the model inventing a new id on its own. I also had to keep the taxonomy from encoding the wrong signal: since being interested in AI was the qualifying trait for the entire population, it had no power to tell candidates apart, so actual matching happened on a smaller set of specific AI sub-paths, like applied ML or AI product, that students and ambassadors actually varied on.

## What I decided was allowed to influence a match

Normalization was also where I decided what the system was allowed to match on at all, and I treated that as an explicit decision rather than something that just falls out of the data. If a student's full free-text bio gets embedded whole, details like age or background that have nothing to do with career fit can silently become part of the similarity score, and an ambassador's name alone can carry signal correlated with gender or ethnicity. So I constructed the fields that fed retrieval explicitly: career paths, roles, skills, goals, and school or field of study, and explicitly excluded names, photos, contact details, age, and any background detail unrelated to career. Logistics like timezone and language were used only as hard eligibility filters that could rule a pairing out entirely, never as something that improved a fit score, so the system wouldn't quietly start preferring people who were geographically or linguistically convenient for reasons that had nothing to do with mentorship quality.

## Making the matches explainable, not just plausible

Because this system was making a real decision about who a student would be paired with, I wanted every match to come with a reason that could actually be checked, not just a plausible-sounding sentence. Each normalized profile produced a flat map of field paths to values, and the matching model was given that map and required to cite specific fields when explaining why it chose an ambassador. A citation that didn't correspond to an actual key in that map was treated as a fabrication, which could be caught with a simple lookup instead of a second model call to check the first one. That grounding step is what let the pipeline return defensible reasons for each of the five matches rather than an unexplained ranked list.

## The API and data model the team built against

Beyond the matching pipeline, I authored the REST and OpenAPI specification and the PostgreSQL data models that the rest of the engineering team built against: more than 20 endpoints across authentication, profiles, discovery, matching, and messaging. I revised them through design review with engineering and product.

## What I validated, and what I'd have done next

I built the prototype end to end and tested it against a synthetic dataset of 60 ambassadors and 50 students, confirming it could take a student profile, normalize it, retrieve candidates, and return five ambassador matches with grounded explanations. My internship ended shortly after, so I don't have visibility into whether it went into production or how real students engaged with it, and I wouldn't want to claim results I can't verify.

If I'd kept working on it, I would have focused on three things. First, scalability and reliability as the system grows from dozens of profiles to hundreds or thousands under concurrent requests, which is where exact in-memory search would stop being reasonable. Second, evaluating real-world match quality: whether students actually engaged with their recommended ambassadors, whether those relationships lasted, and whether the experience genuinely improved students' comfort with AI. Third, and as the way to make the second one possible, an append-only event log that records match outcomes from the first version onward, so that quality could be measured from real history instead of reconstructed after the fact.
